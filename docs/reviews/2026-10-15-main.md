## Summary
You set up a solid foundation for the storefront with Next.js App Router, Tailwind CSS v4, and React 19. The build and test pipelines are operational, and the visual structure reflects the brand goals well. However, the frame cache has a memory retention bug during scrubbing, and its corresponding test does not verify cache eviction. Fixing these points will ensure the mobile performance goals hold up.

## Major
### 🟠 Late resolving frame loads leak into cache and bypass window bounds, `src/lib/canvas/frame-loader.ts:91`
**Problem**: When you scrub quickly across the sequence, updateActiveWindow removes images outside the active window. But images that were already loading remain in pendingLoads. When those loads complete, their onload callback puts them directly into the cache without checking if they are still inside the active window. Also, calling clear does not stop these pending loads from entering the cache upon completion.
**Why it matters**: Scrubbing across the animation sequence causes background image loads to accumulate in memory. Instead of staying capped at the window radius, the cache can grow to hold all 150 frames. This consumes hundreds of megabytes of memory and defeats the 80MB memory safeguard designed to prevent mobile browser crashes.
**Suggested fix**: In the onload callback, check whether the loaded frame index still falls within the active window before adding it to the cache. If the frame is now outside the window, discard the image. Also track an active generation flag so that calling clear cancels or ignores any in flight load callbacks.

### 🟠 Frame cache window test asserts empty cache and skips window eviction, `src/lib/canvas/__tests__/frame-loader.test.ts:66`
**Problem**: The test named bounds frame cache window and clears memory cleanly intends to verify acceptance criterion 6. However, because frame loading is asynchronous and happy dom does not load image assets synchronously, the cache remains at size zero throughout the test run. The test only asserts that zero equals zero before and after clear. It never verifies that frames are cached, never verifies that frames outside the window are evicted, and never tests the memory bounding logic.
**Why it matters**: This leaves the primary mobile memory safeguard completely untested while giving false confidence that the acceptance criterion is verified.
**Suggested fix**: Update the test to simulate loaded frames in the cache. Populate the cache with frame indices across a range, call updateActiveWindow, and assert that frames outside the window radius are removed while frames inside the window remain.

## Minor
### 🟡 addItem accepts non positive quantities and corrupts cart calculations, `src/lib/store/cart-store.ts:40`
**Problem**: addItem does not validate the quantity parameter. If a caller passes zero or a negative number, the store either adds an item with non positive quantity, or reduces an existing item quantity into negative numbers.
**Why it matters**: Invalid quantities distort total item counts and subtotal calculations. A negative subtotal or negative item count could be submitted to checkout or break display math. While updateQuantity correctly removes items when quantity is zero or less, addItem lacks this protection.
**Suggested fix**: Add a guard in addItem that ignores or rejects calls where quantity is zero or negative.

### 🟡 tar extraction command fails on zip archives in Linux environments, `scripts/optimize-frames.mjs:32`
**Problem**: The optimization script uses tar -xf to unpack a zip file. While Windows includes bsdtar which handles zip archives, standard Linux environments use GNU tar which fails when given a zip file.
**Why it matters**: Running npm run optimize:frames on Linux developer machines or continuous integration runners will fail with an error stating that the file is not a tar archive.
**Suggested fix**: Use a pure JavaScript zip extraction library, or check the platform to invoke an extraction utility like unzip on Linux.

### 🟡 Raw localStorage reference risks runtime errors in server rendering, `src/lib/store/cart-store.ts:104`
**Problem**: The store persistence configuration uses createJSONStorage(() => localStorage) directly without checking if window is defined. In standard Node server environments during server rendering, localStorage is undefined.
**Why it matters**: If server rendering code evaluates storage before the client mounts, accessing localStorage throws an error.
**Suggested fix**: Guard the storage getter with a check for typeof window !== "undefined", or provide a fallback storage object for the server environment.
